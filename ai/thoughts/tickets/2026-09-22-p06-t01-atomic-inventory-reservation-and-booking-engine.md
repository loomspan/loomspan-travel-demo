# P06-T01 — Deliver Atomic Inventory Reservation and Booking Record Engine

## Outcome

An authenticated traveler can confirm a simulated booking for any valid Planned itinerary, resulting in atomic reservation of finite catalog inventory (flight seats, stay unit-nights, and rental car intervals), safe handling of concurrent attempts and retries via an idempotency key, generation of realistic fictional confirmation references, and persistent booking snapshot records.

## Requirements

- **Database schema and persistence (`V17__create_booking_schema.sql`):**
  - Create table `detour_booking`:
    - `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`
    - `public_id UUID NOT NULL UNIQUE`
    - `trip_id BIGINT NOT NULL REFERENCES detour_trip(id) ON DELETE CASCADE`
    - `planned_itinerary_id BIGINT NOT NULL REFERENCES detour_planned_itinerary(id)`
    - `booking_reference VARCHAR(20) NOT NULL UNIQUE`
    - `status VARCHAR(20) NOT NULL` with constraint checking `status IN ('ACTIVE', 'CANCELED')`
    - `grand_total_cents BIGINT NOT NULL CHECK (grand_total_cents >= 0)`
    - `idempotency_key VARCHAR(100) NOT NULL`
    - `created_at TIMESTAMP WITH TIME ZONE NOT NULL`
    - `canceled_at TIMESTAMP WITH TIME ZONE`
    - `airfare_reference VARCHAR(20)`
    - `stay_reference VARCHAR(20)`
    - `rental_reference VARCHAR(20)`
    - `rental_occupancy_id BIGINT REFERENCES rental_unit_occupancy(id)`
    - Enforce at most one active booking per trip: unique index on `(trip_id)` where `status = 'ACTIVE'`.
    - Unique index on `(trip_id, idempotency_key)` to guarantee idempotent execution per trip.
  - Create table `detour_booking_item_snapshot` (or snapshot columns) preserving the exact frozen descriptive details and prices of booked components (flights, stays, rental car) at the moment of booking so history never relies on live catalog joins.
- **Fictional confirmation reference generation:**
  - Booking reference: `DT-` followed by 6 uppercase alphanumeric characters (e.g. `DT-K8M2P4`).
  - Airfare confirmation: 6 uppercase alphanumeric characters (airline PNR record locator style, e.g. `W3X8PL`).
  - Stay confirmation: `HT-` followed by 6 uppercase alphanumeric characters (e.g. `HT-4M9Q2P`).
  - Rental car confirmation: `RC-` followed by 6 uppercase alphanumeric characters (e.g. `RC-7T1N5V`).
  - Only generate component references for components present in the booked itinerary; omit / store null for absent optional components.
- **Atomic inventory reservation and locking:**
  - Execute booking inside a single database transaction with deterministic locking order to prevent deadlocks:
    1. Check trip ownership, trip expiration, and existing active booking.
    2. Lock flight instances ordered by `flight_instance.id ASC`.
    3. Lock nightly stay inventory rows ordered by `accommodation_unit_id ASC, night_date ASC`.
    4. Validate and reserve rental unit occupancy.
  - Inventory reservation mechanics:
    - **Airfare:** verify `available_seats >= traveler_count` for outbound and return flight instances. Decrement:
      `UPDATE flight_instance SET available_seats = available_seats - ? WHERE id = ? AND available_seats >= ?`.
    - **Stay:** verify `available_inventory >= unit_count` for each night in the stay interval. Decrement:
      `UPDATE accommodation_nightly_inventory SET available_inventory = available_inventory - ? WHERE accommodation_unit_id = ? AND night_date = ? AND available_inventory >= ?`.
    - **Rental car:** verify the rental unit has no overlapping active occupancy for `[pickup_at, return_at)`. Insert into `rental_unit_occupancy` with `occupancy_status = 'ACTIVE'`. Rely on `RentalUnitOccupancyOverlapTrigger` to guarantee non-overlap.
  - **Conflict handling:**
    - If any component is unavailable (insufficient seats, sold-out room night, occupied rental unit), roll back the transaction entirely. Reserve no components.
    - Return HTTP 409 Conflict with structured, actionable error details specifying exactly which component(s) are unavailable.
- **Pre-booking eligibility and constraints:**
  - Authenticated user must own the trip (404/403 isolation).
  - Trip must not be Expired based on `America/Los_Angeles` departure midnight (`isExpired(startDate)`). Reject expired booking attempts with HTTP 400.
  - Trip must not already have an `ACTIVE` booking. Reject with HTTP 409 Conflict (`ALREADY_BOOKED`).
  - Planned itinerary must exist and belong to the trip.
  - Planned itinerary must contain at least one reservable component (airfare, stay, or rental).
  - Validates client-supplied `expectedVersion` against `detour_trip.version` to prevent booking against stale trip state.
- **Idempotency handling:**
  - Accept an `Idempotency-Key` header or request body parameter.
  - If a booking request with the same idempotency key is received for the same trip:
    - If a booking was already successfully created, return the existing booking record with HTTP 200/201 without decrementing inventory a second time.
- **API endpoints:**
  - `POST /api/trips/{tripId}/bookings`:
    - Payload: `{ "plannedItineraryId": "uuid", "expectedVersion": number, "idempotencyKey": "string" }`
    - Response: HTTP 201 with `BookingResponse` including `bookingReference`, `status`, `bookedAt`, component confirmation references, grand total, and frozen snapshot details.
  - `GET /api/trips/{tripId}/bookings/active`:
    - Returns the current active booking for the trip, or 404 if no active booking exists.
  - `GET /api/trips/{tripId}/bookings`:
    - Returns all historical booking records (active and canceled) for the trip ordered by `created_at DESC`.

## Acceptance criteria

- [ ] Schema migration `V17__create_booking_schema.sql` cleanly establishes `detour_booking` and snapshot structures with required constraints and indices.
- [ ] Attempting to book a valid Planned itinerary decrements flight `available_seats`, accommodation `available_inventory`, and inserts active `rental_unit_occupancy` in a single atomic transaction.
- [ ] If any component has insufficient inventory, the transaction rolls back completely, reserving zero components, and returns HTTP 409 with itemized conflict reasons.
- [ ] Re-sending a booking request with the same `idempotencyKey` returns the existing booking record without deducting inventory again.
- [ ] Attempting to book an itinerary on an Expired trip (evaluated at start of departure date in `America/Los_Angeles`) is rejected.
- [ ] Attempting to book a trip that already has an active booking is rejected with HTTP 409.
- [ ] Booking produces realistic fictional reference numbers (`DT-XXXXXX`, `FL-XXXXXX`, `HT-XXXXXX`, `RC-XXXXXX`) only for components included in the booking.
- [ ] Concurrent booking attempts against the final available seat, room night, or car unit result in exactly one successful booking and clean conflict rejection for the other, without negative inventory or deadlocks.
- [ ] Booking records and component snapshots survive an application restart and are strictly isolated to the authenticated trip owner.
